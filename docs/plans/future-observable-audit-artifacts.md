# Future observable audit artifacts

## Context

The planning audit should help a user understand a system through observed behavior rather than by presenting source code. Its purpose is to give the user enough independent evidence to evaluate an agent-written plan critically. The user does not need to author the plan from scratch to engage deeply with the system.

The first supported artifact is a test trace: RBA runs a selected test through a framework adapter and stores its structured result.

This plan records other evidence types we may add later. They are deliberately not part of the first implementation.

## Intended planning workflow

1. The user describes the desired outcome and discusses it with the planning agent.
2. The agent investigates the current system and builds a small, relevant audit from independently generated behavioral evidence.
3. The user explores that evidence, asks questions, and develops a working understanding of the system.
4. The agent writes a concise draft implementation plan grounded in the audit and its wider investigation.
5. The user verifies the draft against the audit, challenges unsupported assumptions, and edits or rejects it where necessary.
6. The plan becomes actionable only after explicit user approval.

Authorship and authority are separate: the agent may do the work of drafting, but the user retains control over whether the plan is accurate and ready to execute. The audit makes that review substantive rather than asking the user to trust an opaque proposal.

The audit must remain independent of the plan. Agent-authored plan text is not evidence, and changing the plan must not rewrite or reinterpret the underlying artifacts.

## Information hierarchy

RBA should put information at the level where it becomes useful:

- The audit contains structured behavioral evidence.
- The plan is a concise overview of the intended change: outcome, scope, approach, important constraints, unresolved assumptions, and a short task breakdown.
- Tasks contain the implementation detail: affected components, concrete steps, edge cases, acceptance criteria, and checks.
- Chat supports clarification and review. The planning agent should answer the question at hand rather than producing long findings reports, investigation narratives, or conclusions.

The plan should normally fit within one screenful and make the important decisions easy to scan. It should not repeat artifact contents, explain every discovery, or pre-empt the detailed task specifications. Concision must not hide uncertainty: material risks and unsupported assumptions still belong in the overview.

## Product principles

- An artifact is evidence generated from a real system, not an agent-authored explanation.
- An artifact should describe one observation with clear provenance: what was run or queried, when it happened, and whether collection succeeded.
- The UI renders structured data stored by RBA. It does not depend on prose generated by the agent.
- Agent tools should be granular and evidence-specific, such as `add_request_trace` or `add_log_query`, rather than a generic batch artifact tool.
- Framework and vendor details belong behind adapters. The agent asks for an observation without needing to know the installed runner, tracing backend, or log provider.
- Source files and source contents are not audit artifacts. Evidence may identify a runtime symbol or subsystem when a collector reports it, but the audit must not become a route back to browsing code.
- Collection should begin with the smallest observation that can answer the current question. Expensive, broad, or production-facing queries require explicit bounds.
- Material claims in an agent-written plan should be traceable to audit evidence where possible. Assumptions and unresolved questions should be labelled rather than presented as observed facts.
- The planning agent should prefer short, decision-oriented writing. Detail should be added during task decomposition only when it helps an implementation agent execute or verify the work.

## Next planning-flow change

Before adding another artifact type, update the current plan ownership model with the smallest viable change:

1. Give the planning agent a tool that replaces the current draft plan.
2. Update the agent prompt so it drafts a concise plan after gathering and discussing enough evidence, while continuing to maintain the audit separately.
3. Keep the plan directly editable by the user.
4. Ask the agent to identify the audit evidence supporting material steps and to call out unsupported assumptions in the plan.
5. Keep detailed implementation instructions and acceptance criteria out of the overview until the plan is decomposed into tasks.
6. Preserve an explicit user action before the plan can be committed for execution.
7. Test that audit updates never modify the plan and plan updates never modify audit artifacts.

Do not add annotations, per-paragraph approvals, revision history, or automatic evidence links in the first version. Plain artifact identifiers or names in the draft are enough to test whether evidence-grounded review is useful.

## Candidate artifacts

### Runtime call trace

Shows the ordered calls made while exercising one operation, including nesting, duration, errors, and async boundaries where the runtime can report them.

- Useful for: understanding control flow and which components collaborate without reading their implementations.
- Possible collectors: language profiler APIs, OpenTelemetry spans, debugger/probe output, or test-runner instrumentation.
- Stored shape: root operation, ordered spans, parent relationships, runtime symbol names, durations, and errors.
- Main constraint: instrumentation varies significantly by language and can change timing or expose sensitive arguments. Capture names and timing by default, not local variable values.

### Request or interaction trace

Records one externally visible workflow, such as an HTTP request, CLI invocation, background job, or UI interaction, together with its inputs, outputs, and major internal stages.

- Useful for: connecting user-visible behavior to service boundaries.
- Possible collectors: HTTP middleware, browser automation traces, job instrumentation, or CLI wrappers.
- Stored shape: trigger, sanitized input summary, response/result, status, duration, and linked child operations.
- Main constraint: request and response data must be redacted before persistence.

### Log query result

Captures selected log events returned by a bounded query against local or production logs.

- Useful for: seeing how a feature is used in practice, common failure paths, and operational terminology.
- Possible collectors: local structured logs, system journals, or provider-specific APIs behind log adapters.
- Stored shape: provider, environment, immutable query, time range, result count, selected structured events, and redaction metadata.
- Main constraint: production access, secrets, personal data, retention, and potentially high result volume. Queries must have an explicit environment, time range, and result limit.

### Distributed trace

Shows how one request crosses processes or services.

- Useful for: discovering service ownership, queues, retries, fan-out, and remote failure boundaries.
- Possible collectors: OpenTelemetry-compatible tracing systems and vendor-specific tracing APIs.
- Stored shape: trace identifier, sanitized service/span tree, timings, statuses, and selected attributes.
- Main constraint: a trace can contain sensitive attributes and unstable vendor-specific fields. Normalize a small common schema and retain provenance for omitted details.

### Metrics observation

Captures a bounded metric query or comparison, such as request volume, latency distribution, error rate, or queue depth.

- Useful for: testing assumptions about scale, performance, and which paths matter in production.
- Possible collectors: Prometheus-compatible APIs and vendor-specific monitoring adapters.
- Stored shape: query, environment, time range, aggregation, units, series, and collection time.
- Main constraint: charts without query and aggregation context are misleading. Always preserve those inputs and avoid unbounded series.

### Database or persistence trace

Records the persistence effects of one operation: transactions, query classes, affected stores, row counts, and timing.

- Useful for: understanding state transitions, atomicity, and read/write behavior.
- Possible collectors: ORM hooks, database query logs, temporary database snapshots, or transaction instrumentation.
- Stored shape: ordered operations, datastore identity, transaction boundaries, normalized query signature, row count, duration, and errors.
- Main constraint: never store credentials, bound values, or production row contents by default.

### State transition trace

Shows how domain or application state changes in response to one event without exposing the implementation that produced it.

- Useful for: workflows, reducers, state machines, lifecycle rules, and background processing.
- Possible collectors: domain-event streams, reducer instrumentation, state-machine hooks, or before/after snapshots produced by a test harness.
- Stored shape: initial state summary, triggering event, ordered transitions, final state summary, and invariant results.
- Main constraint: state schemas can be large and sensitive. Prefer named states and selected observable fields over complete object dumps.

### Network dependency trace

Records outbound calls made during one test or operation.

- Useful for: discovering external dependencies, retries, caching, and failure behavior.
- Possible collectors: HTTP client hooks, proxy recordings, mock-server histories, or socket instrumentation.
- Stored shape: destination identity, protocol/operation, order, status, duration, retry relationship, and sanitized payload summaries.
- Main constraint: URLs, headers, and bodies frequently contain secrets or user data and require collection-time redaction.

### Configuration and feature-decision trace

Explains which runtime configuration, experiment, permission, or feature-flag decisions affected one operation.

- Useful for: understanding why behavior differs by environment or user cohort.
- Possible collectors: configuration loaders, feature-flag SDK hooks, and authorization decision logs.
- Stored shape: decision name, result, evaluation context summary, source layer, and fallback use.
- Main constraint: do not persist raw secrets, full environment dumps, or identifying targeting attributes.

### Performance profile

Captures where time or resources were spent while running one bounded operation.

- Useful for: identifying hot paths and expensive dependencies without inspecting their code.
- Possible collectors: sampling profilers, allocation profilers, browser performance traces, or runtime diagnostics.
- Stored shape: operation, sample period, aggregated call tree, self/total time, allocation or CPU units, and environment metadata.
- Main constraint: profiles are noisy and environment-dependent. They should state collection conditions and should not be presented as deterministic behavior.

### Failure trace

Captures a reproducible failure with the triggering operation, error chain, relevant runtime events, and cleanup outcome.

- Useful for: understanding error contracts, recovery, and partial side effects.
- Possible collectors: failed test runs, exception instrumentation, crash reports, or bounded log/trace correlation.
- Stored shape: trigger, error types and messages, causal chain, observable side effects, recovery result, and links to related evidence.
- Main constraint: stack frames may reveal source paths and error messages may contain sensitive data. Store a sanitized runtime view and make any source linkage an explicit later decision.

## Suggested order after test traces

1. Validate the evidence-grounded, agent-drafted planning workflow using the existing test traces.
2. Add runtime call traces for test executions. They extend the existing local, repeatable test workflow and answer the immediate control-flow question.
3. Add request or interaction traces. They provide a user-facing unit of behavior and can link to test and call traces.
4. Add bounded log queries. This introduces production evidence once access controls, query limits, and redaction are designed.
5. Add distributed traces and metrics observations. Both need provider adapters and clearer environment/provenance UI.
6. Consider persistence, state, network, configuration, and performance artifacts only in response to concrete planning needs.

## Shared implementation shape

Each artifact type should be introduced vertically rather than by first building a universal artifact platform:

1. Define the user question the artifact answers and a minimal normalized schema.
2. Add one granular agent tool with bounded inputs.
3. Add an adapter interface and one real collector for a framework or provider already used by a target workspace.
4. Sanitize and validate the collector output before it reaches goal storage.
5. Add a purpose-built collapsible renderer that shows provenance before details.
6. Test unsupported environments, failed collection, redaction, size limits, refresh/upsert identity, and removal.
7. Validate the collector against a real workspace before adding another adapter.

Artifacts may later link to one another through stable IDs, for example a request trace linking to a distributed trace and a log query. Do not add that relationship model until at least two implemented evidence types need it.

## Explicitly deferred

- Source-file or code-hunk artifacts.
- Agent-authored summaries presented as evidence.
- Long-form findings documents or investigation reports generated alongside the audit.
- A generic `add_artifact` tool or arbitrary artifact payloads.
- Automatic broad collection at the start of every planning conversation.
- Production log, trace, or metric access before permissions, redaction, bounds, and environment labelling are designed.
- Cross-artifact graphs, timelines, and correlation until multiple evidence types exist.

## Completion criteria for a future artifact type

A new type is ready when the agent can request one bounded observation without knowing the underlying framework or vendor; RBA can collect, sanitize, validate, store, refresh, remove, and render it; unsupported setups fail clearly; and the resulting panel helps a user answer a system-behavior question without opening source code.
